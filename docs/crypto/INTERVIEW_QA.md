# 面试问答准备

以下回答按已保存的项目证据撰写。链上与在线 LLM 的未完成部分要主动说清楚。

## 1. 为什么选择资金费率 carry？

我想研究一个容易被单一指标误导的加密产品：永续合约资金费率看起来很高，但实际结果还取决于基差、现货和永续两条腿的价格变化、手续费、滑点、抵押以及单腿执行风险。因此我把重点放在可解释的产品账本和风险筛选，而不是只追求回测收益。

## 2. 这套策略具体怎么构建？

研究结构是 BTC/USDT 现货多头加 USDⓈ-M 线性永续空头。每条腿单独记账，再汇总 P&L、资金费、手续费和滑点。资金费只有结算后才进入信息集，信号在下一可交易小时执行，避免把结算结果提前当成预测值。

## 3. 结果怎么样？

冻结的 `carry_static` 在一次性 holdout 上是 +0.39%，覆盖 275 个日样本。这个结果很小，样本不到一年，所以年化 Sharpe 和 CAGR 都不稳定。我不会把它说成稳定盈利。更重要的是，独立的保证金代理检查在 development 阶段发现 12,601/19,704 个小时观察低于声明阈值，正向账本结果在这个假设下不可执行。

## 4. 为什么 delta-neutral 也可能有风险？

名义 delta 接近零不等于两腿能同步成交，也不代表抵押现金足够。基差扩大、资金费转负、永续腿先成交而现货腿失败、抵押品估值变化和交易费用都会留下损失。小时级 OHLCV 还看不到订单簿深度和盘中清算，所以我把保证金结果称为代理审计，不称作历史强平模型。

## 5. `funding_filter` 为什么没有改善结果？

开发试验的 `funding_filter` 总收益是 -4.26%，而且有 1,202/17,799 个小时保证金代理下穿。筛选正资金费本身不够：资金费可能覆盖不了两条腿的波动和成本，阈值还必须只基于当时可得信息。这个结果保留在报告里，用来说明研究不能只展示挑中的正结果。

## 6. 你怎样避免前视偏差？

我把每类数据按可用时间而不只是行情时间处理。资金费结算值在结算之后才可知，所以策略只能在下一符合条件的小时开仓。开发、验证与一次性 holdout 分开；AI 事实层也只允许读取 development/validation，不会接触已消费的 holdout。

## 7. AI 在项目里做什么，怎样防止它编数字？

AI 只负责解释一条已审计 trial 的固定事实。收益表和归因直接从 trial artifact 生成；模型输出只允许定性摘要、风险解释、问题和已登记的 evidence ID。伪造指标、未知证据、数值断言、读取 holdout 或改变费用的请求都会被拒绝或回退。当前没有配置真实 provider，所以展示的是确定性报告，不是在线模型调用。

## 8. 链上部分做到了什么？

我实现了 ABI 解码后的 Uniswap 风格 Swap 事件规范化、按交易日志去重、用 canonical block hash 剔除重组记录、按 token decimals 换算并阻止不完整区块范围被汇总。现在的样例是明确标记的合成工程 fixture；这台环境没有可用 archive RPC，所以我没有声称抓取过真实池事件。

## 9. 为什么还要做固定区块 fork？

事件日志说明链上状态发生过变化，但不证明某个用户此刻能按 quote 成交。固定区块 fork 可以检查 allowance、输入/输出余额和 `amountOutMinimum` 失败路径，帮助验证合约交互假设。当前我只完成了本地 Anvil endpoint 的 fail-closed 前置检查；真实 approve/swap/revert 没有运行，因为 Anvil、可用 WSL 和 Docker Engine 都不可用。

## 10. 如果继续做，你会先改什么？

先恢复只读 archive RPC 与本地 Anvil，核验 Ethereum 链、Uniswap V3 池的 token 顺序/decimals/fee 和固定区块哈希，再取不超过 10,000 个区块、每批不超过 1,000 个区块的事件，核对至少三笔交易。之后在 localhost fork 上跑 approve、成功 swap、不可达输出的 revert 和撤销 allowance 用例。只有这些证据通过，才考虑把链上分析接入最终只读工作台。
